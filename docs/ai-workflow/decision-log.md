## 2026-05-06 - MVP 데모를 로컬 AI Workflow로 구현

### 변경 전

초기 검토 단계에서는 Upstage Solar 같은 API 기반 LLM을 사용할 수 있는지 확인했다. 다만 STT까지 Upstage 공개 API로 처리하기는 어려워 보여, API 조합을 쓰려면 별도 STT 서비스가 필요했다.

### 변경 후

MVP 데모는 로컬에서 무료로 실행 가능한 구성으로 구현한다.

```text
브라우저 음성 녹음
→ faster-whisper 기반 STT
→ Ollama 기반 로컬 LLM
→ 시나리오 상태 추적
→ 꼬리 질문 또는 성공/실패 판정
→ 최종 피드백
```

### 변경 이유

현재 목적은 AI 성능 최적화가 아니라 실제 Workflow 검증이다. API 토큰, 과금, 외부 서비스 설정에 의존하기보다 로컬에서 빠르게 실행 가능한 데모를 먼저 만드는 편이 적합하다.

### 성능 영향

로컬 STT와 로컬 LLM은 상용 API보다 품질이 낮거나 응답이 느릴 수 있다. 특히 다음 영역에서 차이가 날 수 있다.

- STT 정확도
- LLM의 한국어 피드백 품질
- structured JSON 출력 안정성
- 응답 속도

다만 이번 단계에서는 성능보다 Workflow 검증이 우선이므로 허용 가능한 차이로 본다.

### 비용 영향

API 토큰 비용이 발생하지 않는다. 최초 모델 다운로드와 로컬 실행 리소스만 필요하다.

### 리소스 영향

`faster-whisper small.en`과 Ollama 7B급 모델을 사용할 경우 로컬 CPU/메모리 사용량이 증가할 수 있다. 로컬 환경에서 느리면 다음 순서로 낮춘다.

```text
STT: small.en → base.en
LLM: 7B instruct 모델 → 더 작은 instruct 모델
```

### 구현 복잡도 영향

API 기반 구현보다 로컬 의존성 설치가 조금 늘어난다. 대신 네트워크/API key 없이 데모를 실행할 수 있고, adapter 구조를 두면 이후 OpenAI/Upstage 같은 외부 API로 교체할 수 있다.

## 2026-05-06 - 개발용 text turn endpoint 추가

### 변경 전

브라우저 음성 입력과 audio endpoint만 사용한다.

### 변경 후

`POST /api/sessions/{session_id}/turns/text` 개발용 endpoint를 추가했다.

### 변경 이유

STT 모델 설치 전에도 시나리오 시작, transcript 평가, slot 업데이트, 꼬리 질문, 피드백 조회까지 AI Workflow를 테스트할 수 있게 하기 위함이다.

### 성능 영향

텍스트 endpoint는 STT 품질, 발음, 녹음 품질을 반영하지 않는다. 따라서 실제 음성 Workflow보다 이해도 점수가 높거나 안정적으로 보일 수 있다.

### 비용 영향

변화 없음. 로컬 실행이므로 API 비용은 발생하지 않는다.

### 리소스 영향

STT 모델을 거치지 않기 때문에 더 가볍고 빠르게 Workflow를 테스트할 수 있다.

### 구현 복잡도 영향

API route가 하나 추가되지만, STT 문제와 LLM/상태 추적 문제를 분리해서 디버깅할 수 있어 전체 구현 리스크는 낮아진다.

## 2026-05-06 - Ollama 미실행 시 local fallback evaluator 추가(폐기됨)

### 변경 전

`/turns/text`와 `/turns/audio`는 모두 Ollama LLM 호출에 의존했다. 로컬에서 Ollama가 실행 중이지 않으면 `127.0.0.1:11434` 연결 실패가 500 에러로 전파됐고, 브라우저 화면에서는 별도 메시지가 표시되지 않아 사용자가 아무 반응이 없다고 느낄 수 있었다.

### 변경 후

Ollama 호출이 실패하면 local rule-based fallback evaluator가 동작한다. fallback은 transcript의 키워드를 기준으로 `drink`, `temperature`, `size`, `for_here_or_to_go` slot을 채우고, 가장 먼저 빠진 slot에 대한 꼬리 질문을 생성한다.

### 변경 이유

현재 목적은 AI 성능 검증이 아니라 Workflow 검증이다. Ollama 설치 여부 때문에 세션 진행, slot 업데이트, 꼬리 질문, 피드백 조회를 테스트하지 못하는 것은 데모 목적과 맞지 않다.

### 성능 영향

Ollama가 정상 실행 중이면 기존처럼 LLM 기반 평가를 사용한다. Ollama가 없을 때는 fallback이 동작하므로 피드백 품질과 의미 해석 범위는 낮아진다. 대신 텍스트 기반 Workflow는 끊기지 않는다.

### 비용 영향

변화 없음. fallback도 로컬 코드이므로 API 비용이 발생하지 않는다.

### 리소스 영향

Ollama 미실행 상태에서는 LLM 모델을 로드하지 않아 더 가볍게 동작한다.

### 구현 복잡도 영향

fallback 규칙 코드가 추가되어 약간 복잡해졌다. 대신 데모 실행 안정성이 높아지고, Ollama 설치 전에도 테스트가 가능해졌다.

## 2026-05-06 - local fallback evaluator 제거 및 Ollama 경고 반환

### 변경 전

Ollama 호출이 실패하면 local rule-based fallback evaluator가 transcript 키워드를 기준으로 slot을 채우고 꼬리 질문을 생성했다.

### 변경 후

Ollama 호출이 실패하면 AI 평가를 진행하지 않고 `503` 응답으로 경고 문구를 반환한다.

```text
Ollama가 실행 중이 아니어서 AI 평가를 진행할 수 없습니다. `ollama serve` 실행 후 다시 시도하세요.
```

### 변경 이유

이번 테스트의 목적은 fallback 규칙이 아니라 Ollama LLM을 활용한 실제 AI Workflow를 확인하는 것이다. fallback이 동작하면 사용자가 Ollama가 사용된 것으로 오해할 수 있어, 실패 상태를 명시적으로 보여주는 편이 더 정확하다.

### 성능 영향

Ollama가 실행 중일 때의 성능은 변하지 않는다. Ollama가 없을 때는 더 이상 임의 점수나 꼬리 질문을 생성하지 않으므로, 실제 AI 평가 품질과 fallback 품질이 섞이지 않는다.

### 비용 영향

변화 없음. 로컬 실행이므로 API 비용은 발생하지 않는다.

### 리소스 영향

Ollama 미실행 시 추가 모델이나 fallback 연산을 수행하지 않는다.

### 구현 복잡도 영향

fallback 규칙 코드가 제거되어 LLM adapter의 책임이 단순해졌다. 대신 API는 `LocalLLMUnavailableError`를 `503` 경고 응답으로 변환한다.

## 2026-05-06 - 이해도 점수 보정 기준과 상황 진행 표시 추가

### 변경 전

LLM 프롬프트는 `understood_score`를 0~100 정수로 반환하라는 정도만 정의했다. 그래서 `I want latte`처럼 의미는 전달되지만 초보자식 표현인 문장에도 모델이 85점 이상을 줄 수 있었다.

브라우저 화면도 이해도와 해석만 보여주고, 어떤 정보가 아직 부족한지 명시하지 않았다.

### 변경 후

프롬프트에 점수 구간과 예시를 추가했다.

```text
I want latte → 약 78점
```

이 문장은 `drink`는 채우지만 `size`, `temperature`, `for_here_or_to_go`는 채우지 못하도록 명시했다. 또한 `interpreted_as`는 사용자가 바로 이해할 수 있게 한국어로 반환하도록 바꿨다.

브라우저 화면에는 턴마다 다음 정보를 함께 보여준다.

```text
이해도 78% · 외국인에게는 라떼를 원한다는 뜻으로 들려요.
상황 진행 1/4
부족한 정보: 온도, 사이즈, 매장/포장
```

### 변경 이유

MVP의 이해도는 시나리오 성공 점수가 아니라 “해당 발화가 통하는지”에 대한 점수다. 다만 화면에서 이 둘을 분리해서 보여주지 않으면 사용자는 “85점인데 왜 아직 질문을 하지?”라고 느낄 수 있다.

따라서 이해도 점수는 더 보수적으로 보정하고, 시나리오 진행도는 별도 정보로 노출한다.

### 성능 영향

모델과 호출 횟수는 그대로다. 프롬프트가 길어져 입력 토큰은 소폭 증가하지만, 로컬 Ollama 실행이므로 API 비용에는 영향이 없다.

품질 면에서는 beginner expression에 대한 점수 일관성이 올라갈 것으로 기대한다. 단, 로컬 7B 모델 특성상 항상 같은 점수를 보장하지는 않는다.

### 비용 영향

로컬 실행이므로 API 비용 변화는 없다.

### 리소스 영향

프롬프트 길이 증가로 LLM 추론 시간이 아주 조금 늘 수 있다. 모델 크기와 메모리 사용량은 변하지 않는다.

### 구현 복잡도 영향

프롬프트와 화면 표시 로직만 변경했다. API schema는 그대로 유지한다.

## 2026-05-06 - 턴별 이해도 제거 및 최종 피드백 일괄 생성으로 변경

### 변경 전

각 사용자 답변마다 LLM이 `understood_score`와 `interpreted_as`를 반환했다. 브라우저 화면도 매 턴마다 다음처럼 보여줬다.

```text
이해도 78% · 외국인에게는 라떼를 원한다는 뜻으로 들려요.
상황 진행 1/4
부족한 정보: 온도, 사이즈, 매장/포장
```

### 변경 후

대화 중 LLM은 다음 2가지만 담당한다.

```text
filled_slots
follow_up_question
```

턴 응답 API에서도 `understood_score`, `interpreted_as`를 제거했다. 사용자는 대화 중에 점수나 피드백을 보지 않고, AI의 꼬리 질문과 상황 진행도만 본다.

최종 피드백은 세션이 `success` 또는 `failure`로 종료된 뒤에만 생성한다. 이때 전체 대화 목록을 LLM에 전달하고 다음 구조로 한 번에 반환한다.

```json
{
  "total_understood_score": 82,
  "summary": "주문 의도는 전달됐고 필요한 정보도 대부분 채워졌습니다.",
  "turn_feedback": [
    {
      "user_said": "I want latte",
      "ai_question": "Would you like it hot or cold?",
      "heard_as": "외국인에게는 라떼를 원한다는 뜻으로 들려요.",
      "better_expression": "Can I get a latte?",
      "reason": "주문 상황에서는 Can I get이 더 자연스럽습니다."
    }
  ]
}
```

### 변경 이유

서비스 핵심 가치는 “말하는 중간에 채점받기”보다 “실제 상황을 끝까지 클리어하고, 끝난 뒤 내 영어가 어떻게 들렸는지 확인하기”에 더 가깝다.

턴마다 점수를 보여주면 사용자가 답변 흐름보다 점수에 집중하게 되고, `85점인데 왜 아직 질문을 하지?` 같은 혼란도 생긴다. 따라서 대화 중에는 부담을 줄이고, 최종 피드백에서 전체 맥락을 기준으로 이해도와 표현 개선을 제공하는 편이 더 자연스럽다.

### 성능 영향

대화 중 턴 평가 프롬프트가 짧아졌다. 각 턴에서 점수와 설명을 생성하지 않으므로 응답이 더 안정적이고 약간 가벼워질 수 있다.

대신 세션 종료 시 최종 피드백 LLM 호출이 추가된다. 전체 대화 transcript를 한 번에 넣기 때문에 종료 시점의 응답 시간은 조금 길어질 수 있다. 다만 MVP에서는 턴 수가 제한되어 있어 리소스 부담은 작다.

### 비용 영향

로컬 Ollama 실행이므로 API 비용은 없다. 외부 LLM API로 전환하면 턴당 토큰은 줄고, 세션 종료 시 피드백 토큰이 추가되는 구조가 된다. 전체적으로는 중간 피드백을 매번 생성하는 방식보다 비용 예측이 쉽다.

### 리소스 영향

대화 중 LLM 출력이 짧아지고, 종료 시점에만 긴 피드백을 생성한다. 메모리 사용량은 모델 크기에 의해 대부분 결정되므로 변화가 작다.

### 구현 복잡도 영향

`TurnEvaluation`은 slot 추적 결과만 담도록 단순해졌다. 대신 `SessionFeedbackGenerator` 책임이 커졌고, 최종 피드백은 세션 종료 후에만 조회되도록 API 검증이 추가됐다.

## 2026-05-06 - 시나리오 종료 후 최종 피드백 자동 생성과 로딩 표시 추가

### 변경 전

시나리오가 끝나면 대화창에는 `Scenario cleared.`가 표시됐지만, 최종 피드백 영역은 즉시 바뀌지 않았다. 사용자는 피드백 조회 버튼을 다시 눌러야 한다고 느낄 수 있었고, Ollama가 최종 피드백을 생성하는 동안 응답이 늦으면 화면이 멈춘 것처럼 보였다.

### 변경 후

턴 응답의 `scenario_result`가 `success` 또는 `failure`가 되는 즉시 프론트엔드가 자동으로 `/feedback`을 호출한다. 호출 중에는 최종 피드백 영역에 다음 로딩 상태를 표시한다.

```text
시나리오가 끝났습니다. 최종 피드백 생성 중입니다...
```

수동 피드백 조회 버튼도 요청 중에는 비활성화해서 중복 요청을 막는다.

### 변경 이유

최종 피드백은 서비스의 핵심 결과 화면이므로 사용자가 별도 버튼을 눌러 찾아가게 만들 필요가 없다. 특히 로컬 Ollama는 최종 피드백 생성에 수십 초가 걸릴 수 있어, 로딩 상태를 보여줘야 사용자가 현재 작업이 진행 중임을 이해할 수 있다.

### 성능 영향

LLM 호출 횟수는 기존 수동 조회와 동일하다. 다만 이제 종료 직후 자동으로 호출되므로 사용자가 기다리는 시점이 명확해진다.

### 비용 영향

로컬 Ollama 실행이므로 API 비용 변화는 없다. 외부 API로 전환해도 수동 조회를 자동 조회로 바꾼 것이므로 세션당 피드백 생성 비용은 동일하다.

### 리소스 영향

중복 클릭 방지를 추가해 같은 세션의 피드백 생성 요청이 동시에 여러 번 발생하는 일을 줄인다.

### 구현 복잡도 영향

프론트엔드에 `isFeedbackLoading`, `setFeedbackLoading` 상태가 추가됐다. Backend API 구조는 변하지 않았다.

## 2026-05-06 - 최종 피드백의 한국어 의도 설명 자연화

### 변경 전

최종 피드백의 `heard_as` 필드는 “외국인이 어떻게 이해했는지”를 설명해야 했지만, 프롬프트가 이를 자연스러운 한국어 의도 설명으로 충분히 제한하지 않았다. 그래서 로컬 LLM이 다음처럼 직역체 또는 음차가 섞인 문장을 만들 수 있었다.

```text
외국인에게는 "소마일라떼를 주세요"라고 말했으며, 크기에 대한 요청이 잘 이해되었습니다.
```

### 변경 후

`heard_as`는 한국어 번역문이 아니라 의미 설명으로 쓰도록 변경했다. 이 필드는 더 이상 LLM이 직접 쓰지 않고, 서버가 `filled_slots`를 기준으로 생성한다.

```text
외국인은 작은 사이즈를 원한다는 뜻으로 이해할 가능성이 높아요.
```

최종 피드백 LLM은 더 나은 영어 표현과 이유를 생성한다. `heard_as`와 전체 요약은 서버에서 세션 결과와 slot을 기준으로 자연어 문장으로 채운다.

### 변경 이유

사용자가 확인하고 싶은 것은 “내 영어가 한국어로 어떻게 번역되는지”가 아니라 “상대가 어떤 의도로 이해했는지”다. 따라서 직역문보다 자연스러운 의도 설명이 제품 가치에 더 맞다.

### 성능 영향

프롬프트가 조금 길어졌고, 서버 후처리 조건이 추가됐다. LLM 호출 횟수와 모델은 변하지 않는다.

### 비용 영향

로컬 Ollama 실행이므로 비용 변화는 없다. 외부 API로 전환해도 입력 토큰이 소폭 늘어나는 정도다.

### 리소스 영향

서버 후처리는 문자열 패턴 검사와 간단한 slot 매핑이므로 리소스 영향은 사실상 없다.

### 구현 복잡도 영향

`heard_as` 후처리 함수, 세션 요약 함수, slot별 한국어 표현 매핑이 추가됐다. 대신 LLM 출력 품질이 흔들릴 때도 사용자가 보는 “외국인이 이해한 의미”의 최소 품질을 보장할 수 있다.

## 2026-05-06 - slot 추적과 꼬리 질문을 deterministic guardrail로 보강

### 변경 전

대화 중 slot 추적과 꼬리 질문은 LLM 응답을 우선 사용했다. 따라서 이미 `I want ice latte`에서 온도를 말했더라도, 이후 LLM이 다시 다음처럼 온도를 물을 수 있었다.

```text
Would you like your latte ice or hot?
```

또한 `here`처럼 짧은 답변은 LLM이 `for_here_or_to_go` slot으로 안정적으로 추출하지 못하면, 실제로는 답변을 했는데도 턴 제한에 걸려 실패할 수 있었다.

### 변경 후

대화 중에는 다음 guardrail을 추가했다.

```text
1. transcript에서 명확한 cafe slot을 rule-based로 한 번 더 추출
2. 기존에 채워진 slot은 덮어쓰지 않음
3. 꼬리 질문은 LLM 질문을 그대로 쓰지 않고 실제 missing slot 기준 template 사용
```

예를 들어 다음 입력은 LLM이 흔들려도 서버가 slot을 채운다.

```text
I want ice latte → drink=latte, temperature=iced
small please → size=small
here → for_here_or_to_go=for here
I'm to go → for_here_or_to_go=to go
```

### 변경 이유

MVP의 핵심은 자유 대화를 잘하는 것이 아니라 시나리오를 안정적으로 클리어하는 것이다. 필수 slot이 이미 채워졌는지와 다음에 무엇을 물어야 하는지는 LLM 자유문장보다 서버 상태를 기준으로 판단해야 한다.

### 성능 영향

대화 중 LLM 호출 횟수는 변하지 않는다. 다만 꼬리 질문 생성은 서버 template을 사용하므로 LLM이 만든 부정확한 질문을 그대로 노출하는 위험이 줄어든다.

### 비용 영향

로컬 Ollama 실행이므로 비용 변화는 없다. 외부 API로 전환해도 호출 횟수는 동일하다.

### 리소스 영향

rule-based slot 추출은 문자열 검사 수준이라 리소스 영향은 사실상 없다.

### 구현 복잡도 영향

`extract_slots_from_transcript`와 기존 slot 보존 로직이 추가됐다. 대신 LLM 출력이 흔들려도 시나리오 진행 상태와 성공/실패 판정이 더 안정적이다.

## 2026-05-06 - 더 나은 표현 피드백을 slot 기반으로 안정화

### 변경 전

최종 피드백에서 LLM이 각 답변의 `better_expression`과 `reason`을 생성했다. 이때 모델이 사용자 답변을 고쳐주는 대신 AI가 했어야 할 질문을 제안하는 문제가 생길 수 있었다.

```text
내 답변: I want small latte
더 나은 표현: Do you want it to go or here?
```

### 변경 후

`better_expression`과 `reason`도 turn에서 새로 채워진 slot을 기준으로 서버가 생성한다.

```text
I want small latte → Can I get a small latte, please?
here → For here, please.
I'm to go → To go, please.
```

### 변경 이유

사용자가 원하는 피드백은 “내 답변을 어떻게 더 자연스럽게 말할 수 있는가”다. LLM이 전체 대화 문맥을 보고 다음 질문이나 다른 slot을 섞어 제안하면 피드백 신뢰도가 떨어진다.

### 성능 영향

최종 피드백에서 LLM이 생성해야 하는 항목이 줄어든다. 로컬 Ollama 응답 시간이 더 짧아질 수 있고, 출력 JSON이 흔들릴 가능성도 줄어든다.

### 비용 영향

로컬 실행에서는 비용 변화가 없다. 외부 API로 전환하면 출력 토큰이 줄어 비용이 소폭 줄 수 있다.

### 리소스 영향

서버 문자열 조합 수준이므로 리소스 영향은 거의 없다.

### 구현 복잡도 영향

slot 기반 영어 표현 매핑이 추가됐다. 대신 최종 피드백 품질이 LLM 출력에 덜 의존하게 됐다.
